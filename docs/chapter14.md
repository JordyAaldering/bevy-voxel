# Serialization

We're very close to being able to spawn structures in our world.
The phased chunk generation was an important step, but there is one more thing we need before we can start adding structures: serialization.
Serialization is the process of converting internal Rust data into a format that can be saved to disk, and deserialization is the reverse.
We actually already did this before for the telemetry server, using JSON to send metrics over the network.

Why do we need serialization?
We don't have to; we could just make a function that spawn a tree at a given position.
However, as soon as we want some variation, perhaps some other structures, and a convenient way to observe and modify structures, we'll want them in a more convenient format.
Rather than making a temporary function that we have to replace later, we're better off doing it properly now.

That is not to say you should never take the easy approach, but you should be aware when none of the work you have done will be reusable later.
We have lots of temporary and partially complete systems, but they are all naturally evolving.
It's a trade-off you'll have to make for every feature, you'll almost never be able to immediately implement an intended feature in its entirety because so much depends on so much else.

## Serialization formats

We have two kinds of data.
Data that is generated by the game, and is only used internally, like chunk data.
Data that may come from outside sources, like spritesheets, structures, or setting files.
The former are typically very large files, that are not intended for manual editing.
The latter are typically smaller files, for which it can be convenient to allow manual editing.

That means we want to use different serialization formats for each.
For the first kind we want an efficient and compact binary format.
The [bincode](https://crates.io/crates/bincode) crate is sadly no longer maintained, but the readme suggests some alternatives, pick the one that you prefer.
We already use the JSON format for the telemetry server, so here I'll choose to reuse it, but any similar format would work.

## Steps performed

1. Enable wincode's derive feature and derive `SchemaWrite`/`SchemaRead` for chunk data types. Skip the runtime-only ECS entity field.
2. Save each chunk to `savedata/world/chunk_<x>_<z>.bin`, and save the player's position in `savedata/world/world.bin`. Write through a temporary file before renaming it into place.
3. When spawning a chunk, load its saved voxel data if available; otherwise create and generate a new chunk. Loaded chunks need their mesh rebuilt.
4. Save chunks when they are unloaded and save all in-memory chunks plus the player position on application exit. Restore the player's saved position at startup.
